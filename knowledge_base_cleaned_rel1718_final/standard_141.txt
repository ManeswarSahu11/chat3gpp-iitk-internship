Title Path: Scope
Content: The present document specifies the group management protocols needed to support Mission Critical Services (MCSs). Group management applies only when the UE operates on the network. MCSs are services that require preferential handling compared to normal telecommunication services, e.g. in support of police or fire brigade. MCSs can be used for public safety applications and also for general commercial applications (e.g., utility companies and railways). The present document is applicable to User Equipment (UE) supporting the group management client (GMC) functionality, to application servers supporting the group management server (GMS) functionality, and to application servers supporting the Mission Critical Push To Talk (MCPTT), the Mission Critical Video (MCVideo) and Mission Critical Data (MCData) server functionality.

Title Path: Procedures > Introduction
Content: This clause specifies procedures enabling a group management client (GMC) and an MCS server to manage group documents in a group management server (GMS).
Title Path: Procedures > Common procedures > General
Content: This subclause contains common procedures applied on HTTP signalling specified in the present document.
Title Path: Procedures > Common procedures > General client (GC) procedures > General
Content: GC procedures are usable by both GMC and MCS server.
Title Path: Procedures > Common procedures > General client (GC) procedures > Accessing group document by group ID
Content: In order to address an existing group document defining a group ID known by GC, the GC shall set the Request-URI of an HTTP request to a XCAP URI identifying a group document addressed by a group ID as described in subclause 7.2.10.2, where the group ID is set to the group ID known by GC and where the XCAP root URI is the XCAP root URI configured in the GC.
Title Path: Procedures > Common procedures > Group management client (GMC) procedures
Content: The GMC shall send the HTTP request over a TLS connection as specified for the HTTP client in the UE in annex A of 3GPP TS 24.482 . The GMC shall perform the procedures in subclause 6.2.2 specified for GC.
Title Path: Procedures > Common procedures > MCS server procedures
Content: The MCS server shall send the HTTP request as specified for the HTTP client in the network entity in annex A of 3GPP TS 24.482 . The MCS server shall perform the procedures in subclause 6.2.2 specified for GC.
Title Path: Procedures > Common procedures > Group management server (GMS) procedures > General
Content: The GMS shall handle the HTTP request as specified for the HTTP server in annex A of 3GPP TS 24.482 . The GMS server shall send the HTTP request as specified for the HTTP client in the network entity in annex A of 3GPP TS 24.482 . The GMS shall be configured with own public service identity for accessing documents. The GMS shall be configured with an authorized GMS list, containing: [ a) ] own public service identity for accessing documents; and public service identities for accessing documents of GMSs of MCS providers which are partners of the MCS provider of the GMS. The GMS shall be configured with an authorized MCS server list, containing public service identities of MCS servers of the MCS provider of the GMS. The GMS shall handle SIP requests and SIP responses as specified in 3GPP TS 24.229 .
Title Path: Procedures > Common procedures > Group management server (GMS) procedures > Configuration for access to group document of another MCS provider or to MCS GKTP document of another MCS provider
Content: The GMS shall be configured with a group ID routing database. The group ID routing database consists of mapping of a group ID of another MCS provider to: [ a) ] an XCAP root URI of the MCS provider; and a public service identity for accessing documents of the MCS provider.
Title Path: Procedures > Common procedures > Group management server (GMS) procedures > Forwarding HTTP request accessing a group document of other MCS provider
Content: If the GMS receives an HTTP request with Request-URI identifying a group document addressed by a group ID as described in subclause 7.2.10.2 and the group ID in the Request-URI identifies a group of another MCS provider, then GMS: [ a) ] shall derive XCAP root URI of the other MCS provider using the group ID routing database as specified in subclause 6.2.5.2 and the group ID in the Request-URI; shall replace the XCAP root URI of the Request URI with the derived XCAP root URI of the other MCS provider; if the X-3GPP-Asserted-Identity header field is not present in the received HTTP request, shall insert an X-3GPP-Asserted-Identity header field with the identity of the sender of the HTTP request determined as specified in 3GPP TS 24.482 ; if the Authorization header field is present in the received HTTP request, shall remove the Authorization header field from the HTTP request; and shall forward the HTTP request.

Title Path: Procedures > Group management procedures > Group document creation procedure > General
Content: This procedure enables the GMC to create a group document in GMS.
Title Path: Procedures > Group management procedures > Group document creation procedure > Client procedures > General client (GC) procedures
Content: In order to create a group document, a GC shall create an XML document of the application usage specified in subclause 7.2.1 and shall send the XML document to the network according to procedures specified in IETF RFC 4825 "Create or Replace a Document". The GC shall set the Request-URI of the HTTP PUT request to an XCAP URI in user's tree where the XUI is set to a group creation XUI configuration parameter.
Title Path: Procedures > Group management procedures > Group document creation procedure > Client procedures > Group management client (GMC) procedures
Content: In order to create a group document, a GMC shall perform the procedures in subclause 6.3.2.2.1 specified for GC. NOTE: When the GMC has not received the assigned MCS group ID from the GMS, the GMC can set empty value to the "uri" attribute of the list-service element of the group element of the XML document specified in subclause 7.2.1. Upon reception of an HTTP 409 (Conflict) response with at least one alt-value element in the uniqueness-failure error element, the GMC may repeat procedures of the present subclause and identify the MCS group being created with an MCS Group ID indicated in an alt-value element.
Title Path: Procedures > Group management procedures > Group document creation procedure > Group management server (GMS) procedures
Content: Upon reception of an HTTP PUT request where the Request-URI of the HTTP PUT request identifies an XML document of the application usage specified in subclause 7.2 then the GMS: [ a) ] shall determine the identity of the sender of the received HTTP PUT request as specified in subclause 6.2.5; if the identity of the sender of the received HTTP PUT request is not authorized to initiate group creation, shall respond with a HTTP 403 (Forbidden) response to the HTTP PUT request and shall not continue with rest of the steps; if value of the "uri" attribute of the list-service element of the group element of the XML document specified in subclause 7.2.1 of the received HTTP PUT request does not conform to local policy, shall respond with an HTTP 409 (Conflict) response to the HTTP PUT request. The uniqueness-failure error element shall identify the error condition. The GMS shall include at least one alt-value element in the uniqueness-failure error element, whereby each alt-value element contains an MCS Group ID acceptable for the GMS. The GMS shall not continue with rest of the steps; and shall support receiving an XML document of the application usage specified in subclause 7.2.1 according to procedures specified in IETF RFC 4825 "PUT Handling" where the Request-URI of the HTTP PUT request identifies an XML document of the application usage specified in subclause 7.2.

Title Path: Procedures > Group management procedures > Group document subscription and notification procedure > General
Content: This procedure enables the GMC to subscribe to notification of changes of: [ a) ] one or more MCS group documents; GKTPs elements of one or more MCS GKTP documents; or both. This procedure enables the MCS server to subscribe to notification of changes of: a) one or more MCS group documents. This procedure enables the GMS owning a constituent MCS group of a temporary MCS group to subscribe to notification of changes of: [ a) ] an MCS group document of the temporary MCS group; a GKTPs element of an MCS GKTP document for the temporary MCS group; or both. The group management procedures are MC service agnostic. However, for historical reasons the procedures use MCPTT elements to populate the service specific MIME bodies, header fields and header field parameters. The GMC uses the access token received during authentication.
Title Path: Procedures > Group management procedures > Group document subscription and notification procedure > Client procedures > Group management client (GMC) procedures
Content: In order to subscribe to notification of changes of: [ a) ] one or more MCS group documents of MCS groups identified by MCS group IDs; GKTPs elements of one or more MCS GKTP documents for MCS groups identified by MCS group IDs; or both; a GMC shall send an initial SIP SUBSCRIBE request to the network according to the UE originating procedures specified in 3GPP TS 24.229 and IETF RFC 5875 . In the initial SIP SUBSCRIBE request, the GMC: [ a) ] shall include an application/resource-lists+xml MIME body . In the application/resource-lists+xml MIME body , the GMC shall include one entry element for each document or element to be subscribed to, such that the "uri" attribute of the entry element: contains a relative path reference: [ A) ] with the base URI being equal to the XCAP root URI configured in the GMC; and identifying a group document addressed by a group ID as described in subclause 7.2.10.2 where the group ID is set to the MCS group ID; or contains a relative path reference: [ A) ] with the base URI being equal to the XCAP root URI configured in the GMC; with the document selector identifying the MCS GKTP document as described in subclause 7.7.10 where the group ID is set to the MCS group ID; and with the node selector identifying a GKTPs element of the MCS GKTP document; shall set the Request-URI to the configured public service identity for performing subscription proxy function of the GMS; shall include an application/vnd.3gpp.mcptt-info+xml MIME body with the mcptt-access-token element set to the value of the access token received during authentication procedure as described in 3GPP TS 24.482 ; if identity hiding is required: shall perform the confidentiality protection procedures and integrity protection procedures defined in 3GPP TS 24.379 for MCPTT client on the application/vnd.3gpp.mcptt-info+xml MIME body and on the application/resource-lists+xml MIME body; and shall include an application/mikey MIME body with the CSK as specified in 3GPP TS 24.379 ; shall include the ICSI value "urn:urn-7:3gpp-service.ims.icsi.mcptt" (coded as specified in 3GPP TS 24.229 ), in a P-Preferred-Service header field according to IETF RFC 6050 ; and shall include the g.3gpp.icsi-ref media feature tag containing the value of "urn:urn-7:3gpp-service.ims.icsi.mcptt" in the Contact header field. Upon receiving a SIP NOTIFY request associated with a subscription created as result of the sent initial SIP SUBSCRIBE request: if identity hiding is required, the GMC shall perform the confidentiality protection procedures and integrity protection procedures defined in 3GPP TS 24.379 for MCPTT client; and shall handle the SIP NOTIFY request according to IETF RFC 5875 . In order to re-subscribe to notification of changes of a modified list of: [ a) ] one or more MCS group documents of MCS groups identified by MCS group IDs; GKTPs elements of one or more MCS GKTP documents for MCS groups identified by MCS group IDs; or both; a GMC shall send a SIP re-SUBSCRIBE request to the network according to the UE originating procedures specified in 3GPP TS 24.229 and IETF RFC 5875 . In the SIP re-SUBSCRIBE request, the GMC: [ a) ] shall include an application/resource-lists+xml MIME body . In the application/resource-lists+xml MIME body , the GMC shall include one entry element for each document or element to be subscribed to, such that the "uri" attribute of the entry element: contains a relative path reference: [ A) ] with the base URI being equal to the XCAP root URI configured in the GMC; and identifying a group document addressed by a group ID as described in subclause 7.2.10.2 where the group ID is set to the MCS group ID; or contains a relative path reference: [ A) ] with the base URI being equal to the XCAP root URI configured in the GMC; with the document selector identifying the MCS GKTP document as described in subclause 7.7.10 where the group ID is set to the MCS group ID; and with the node selector identifying a GKTPs element of the MCS GKTP document; if identity hiding is required, shall perform the confidentiality protection procedures and integrity protection procedures defined in 3GPP TS 24.379 for MCPTT client on the application/vnd.3gpp.mcptt-info+xml MIME body and on the application/resource-lists+xml MIME body using the CSK included in the initial SIP SUBSCRIBE request ; and shall include the g.3gpp.icsi-ref media feature tag containing the value of "urn:urn-7:3gpp-service.ims.icsi.mcptt" in the Contact header field.

Title Path: Procedures > Group management procedures > Temporary MCS group formation procedure > General
Content: This procedure enables a GMC to initiate creation of a temporary MCS group by combining MCS groups. NOTE: The temporary MCS group formation procedure does not ensure that the MCSs of the temporary MCS group are the same as MCSs of each constituent MCS group of the temporary MCS group.
Title Path: Procedures > Group management procedures > Temporary MCS group formation procedure > Group management client (GMC) procedures
Content: In order to form a temporary MCS group, a GMC shall send a HTTP POST request according to procedures specified in IETF RFC 9110 and subclause 6.2.3. In the HTTP POST request, the GMC: [ a) ] shall set the Request-URI to an XCAP URI: in users tree where the XUI is set to a group creation XUI configuration parameter; and with the document selector identifying the temporary MCS group to be created; and shall include an application/vnd.3gpp.GMOP+xml MIME body containing a GMOP document requesting group regroup creation specified in subclause 7.3.4.3, with a group element containing a group document for an MCS group. In the group document, the GMC shall include the on-network-temporary element according to subclause 7.2. In the on-network-temporary element, the GMC shall include constituent-MCPTT-group-IDs element according to subclause 7.2. In the constituent-MCPTT-group-IDs element, the GMC shall include one constituent-MCPTT-group-ID element according to subclause 7.2 for each MCS group to be combined. Upon reception of an HTTP 2xx response to the sent HTTP POST request, the GMC shall consider the temporary MCS group formation as successful. Upon reception of an HTTP 409 (Conflict) response with at least one alt-value element in the uniqueness-failure error element, the GMC may repeat procedures of the present subclause and identify the temporary MCS group being formed with an MCS Group ID indicated in an alt-value element.

A group document is an MCData group document only if: [ a) ] the supported-services element is present in the group document; the service child element of the supported-services element is present; and the service element includes the "enabler" attribute set to: the ICSI value for mission critical data (MCData) communications short data service (SDS) specified in the 3GPP TS 24.282 ; the ICSI value for mission critical data (MCData) communications file distribution (FD) specified in the 3GPP TS 24.282 ; or the ICSI value for mission critical data (MCData) communications enhanced service (ES) specified in the 3GPP TS 24.282 . Title Path: Coding > MCS group key transport payloads (GKTP) document coding > Resource interdependencies
Content: The following applies for a MCS GKTP document: [ a) ] a MCS GKTP document shall be associated with an MCS group document in the users tree of a particular user which defines the group ID; a MCS GKTP document shall exist for each associated MCS group document; GMS shall create a MCS GKTP document when the associated MCS group document is created; and GMS shall generate the GMK(s) of the MCS GKTP document according to the presence and values of, or the absence of, the protect-media element, the protect-floor-control-signalling element and the require-multicast-floor-control-signalling element of the associated MCS group document. NOTE: 3GPP TS 33.180 describes how GMK(s) and MKFC(s) are generated.
Title Path: Coding > MCS group key transport payloads (GKTP) document coding > Authorization policies
Content: MCS GKTP documents shall not be managed using XCAP. MCS GKTP documents can be fetched using SIP. An authenticated identity is authorized to subscribe to notification of changes of an GKTPs element of an MCS GKTP document if: [ a) ] the authenticated identity is a member of an MCS group defined by an MCS group document associated with the MCS GKTP document; or the authenticated identity is listed in the authorized GMS list specified in subclause 6.2.5.1 and the subscription is on behalf of a constituent MCS group of the MCS group defined by an MCS group document associated with the MCS GKTP document.
